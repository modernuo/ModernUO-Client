# M1: draw and present at the window display rate

`settings.json`: `"present_at_display_rate": true` (default true since the 2026-11-13 owner decision). Both world renderers use the same controller pacing. The polling loop still runs Update, SDL input, network drain/flush, timers, UI updates, cursor and audio every iteration. A suppressed frame calls FNA SuppressDraw and never enters Draw or EndDraw. There is no sleep in this polling path. This is software pacing, not synchronization to the monitor's scanout phase.

## Default-on migration

`settings_version` is 1 for newly created settings. The source-generated deserializer treats a missing version as 0. `ConfigurationResolver.Load` migrates versions below 1 to `present_at_display_rate=true` and persists the version immediately through the existing atomic save, before command-line overrides or session changes. Old stored false values were written by the former hidden default and are intentionally replaced once. A user can then set false with version 1 retained; subsequent loads preserve both switch states. Current and future versions are not migrated or rewritten on load. If saving fails, the existing save path logs the I/O error; a file that remains unversioned will be migrated again on its next successful load.

The debug overlay labels presented FPS and retains loops/s separately. DevBench reports both and divides effect applies by completed presents. FrameStats' human text says presented frames/FPS; its JSON `frames` and `fps` fields retain their presented-frame meaning. CUO_DIAG retains its existing counters and adds `fps_kind=presented`; CPU ms/s remains indicative on a busy machine. No pacing, focus, minimized, event-loop or vsync policy changed in this default promotion.

Throughput tools (`tools/fps-test`, `tools/aot-bench`, PGO collection, parity and fault-repro drivers) now write `settings_version=1` and explicit `present_at_display_rate=false`; fps-test also starts its plan with `presentcap:off`. DevBench/FrameStats do not override the switch themselves. Other custom plans/jobs that need uncapped draws must explicitly choose off with the current settings version, or issue `presentcap:off` after load. Compare alloc/present together with allocations/s when Update counts differ.

Fresh default-promotion jobs and scripts live in `cuo-poc-state/measure/present-default/`. ## Policy

- Only FPS setting 0 and vsync off qualify. An explicit FPS cap, including one above refresh, retains the existing policy. DevBench/FrameStats forcing the effective interval to zero does not override an explicit nonzero FPS setting for this switch.
- Vsync takes precedence; software display pacing is disabled while vsync is enabled.
- Existing minimized suppression and inactive FPS reduction take precedence. An unfocused client with inactive reduction disabled remains eligible. Minimized Update throttling and event-loop maximum waits keep their existing behavior.
- `event_loop` uses the absolute draw deadline alongside its socket/input wake, queued actions, player-step deadline and maximum wait. Early network/input wakes update without drawing until due. If the event waiter is unavailable or backs off, polling continues without a sleep in this path.
- SDL_GetDisplayForWindow chooses the window's display (SDL's choice for spanning windows). SDL_GetCurrentDisplayMode supplies the fractional refresh rate. Poll once per second while enabled or checked: monitor changes, unplug/replug and refresh changes reset pacing. There can be up to one second of the old rate during a change. Zero, unavailable or nonfinite refresh falls back to the old uncapped path; no guessed 60 Hz limit.
- Deadlines are integer Stopwatch ticks, with rounded frequency/Hz period. Next is previous deadline plus period; missing a whole period resynchronizes to now plus period, without catch-up bursts. Disabling/re-enabling or changing displays resets the phase and permits an immediate first draw.
- DevBench and FrameStats honor the switch; they do not silently uncap Draw. Pickscan and renderer flip stress advance their frame counters on completed presents. Other time-based automation continues on Update. FrameStats alloc/frame and phase totals describe one presented frame, including all intervening Updates; compare allocations/second too when loop counts differ.

## Draw-owned state

SelectedObject, healthbar/container selection, overhead ordering and UI draw state retain the last rendered result between draws. Input continues every Update; visual picking can therefore lag by a display period plus any stall, as with an ordinary render cap. The gate scans picking at actual presented frames using Input.Mouse.Override, with no OS cursor movement.

Mobile/item/effect animation advances and text lifetime/alpha use Update/game time. World-object fades previously took one fixed 25-alpha step per draw opportunity after a 20 ms timer. The paced path carries elapsed fade steps, preventing a 60 Hz draw loop from stretching a 20 ms fade clock to 33 ms. The old path keeps its previous fade behavior. Weather Draw already advances by elapsed Time.Ticks, so no skipped-draw simulation is called in this path (that minimized-only helper resets the particle clock). World-settle time is not paused between display draws; residency and asset preparation still run in Update.

## Counters and checker

The UI FPS number counts completed EndDraw calls, alongside loops/s. LoopStats separates actual draws, completed presents and drains and logs CPU ms/s. CUO_DIAG keeps separate updates/draws/presents/drains, raw ping samples and per-ping maximum Update interval. Its maximum Update duration now measures individual Updates, not the accumulated Updates between presents. FrameStats sums packet counts across intervening Updates and accumulates loop gaps separately from Update work.

`CUO_PRESENT_CAP_CHECK=1` is compiled only under CUO_DEVTOOLS. Every five seconds it logs switch/active state, refresh Hz, draws/s, presents/s, updates/s, old draw decisions, avoided draws, maximum present gap, period and late/over-rate mismatch counts. It shadows the original draw decision on the same input; it does not execute a second Draw/Present, which would defeat the feature and change GPU state. Correctness mismatches are an active presents/s rate above refresh * 1.05, an active draw when the cap says not due, a second draw without a present, or a present without a draw. Present gaps over period + 1 ms increment `late`; late counts and maximum gaps are indicative timing only and do not increment mismatches. State transitions reset its window; the checker includes the current Update in the ending window (one-event boundary tolerance).

Additional work counters: FillGameObjectList full calls, walked objects and glyph quads; Uo.Render buffer/texture upload calls and bytes; FNA batch vertex-buffer upload calls and bytes. Texture atlas loaders outside these probes and native-driver internal copies are not counted. This base has no full-prepare reuse path: reuse hits are zero; M2 owns that work.

## Follow-up: event-loop send latency

The original controller flushed at the packet phase, before plugin/scene/UI updates and queued actions (`GameController.cs:708` at 7d4018ad8, before Scene.Update). `NetClient.Send` (`Network/NetClient.cs:707` at 7d4018ad8) skipped `SendQueuedWake` on the main thread, assuming that Update would flush it. A ping produced by Scene.Update therefore sat through the current Draw/Present or suppressed-frame wait until the next Update. With `event_loop` active, Flush now runs after base.Update (`GameController.cs:832`), before either drawing or waiting. All queued sends signal the sticky wake, including main-thread Draw hooks that run after that flush. Polling retains its old flush position. `event_loop` remains default off; `present_at_display_rate` is now default on.

The Windows inline waiter binds/rearms before Drain (`GameController.cs:677`, `Loop/Win32LoopWaiter.cs:80-99`) and waits on FD_READ/FD_CLOSE (`Loop/Win32LoopWaiter.cs:137`). A repeated loopback test (including arrivals after empty drains and during waits) passes without changing the socket implementation. Readability cannot interrupt synchronous Draw/Present: when that work occupies a full display period, the next drain still waits for it, and EventLoopWait's computed deadline (`GameController.cs:179-193`) may already be due so no native wait occurs; its call after presentation is `GameController.cs:1035`. In bench-000728 GPU cap-on/event-on, median send-wait and wire+poll were 9.505 and 9.824 ms, with 111.7 Updates/s; this is consistent with two draw-length service gaps, not proof of lost socket wakes. The safe local send fix removes the first gap; receiving during Draw would require a different transport/dispatch architecture, outside this follow-up. Re-run counts rather than predicting its latency benefit.

The bench-000728 Legacy output contained the just-finished GPU diagnostic file: the collector's previous launch-minus-one-second mtime test admitted it. Corrected parsing excludes it and reports source windows; old table.txt Legacy medians that included it are invalid. The parser also removes pre-measurement startup windows. Historical results are not measurements of the follow-up binary.
